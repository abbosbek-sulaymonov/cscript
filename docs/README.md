## The shape of the thing

```
source ──▶ lexer ──▶ parser ──▶ type checker ──▶ compiler ──▶ VM
                       │             │              │          │
                      AST      annotated AST     bytecode    values
                                                                │
                                          hot ─▶ typed IR ─▶ arm64
```

Five stages, one pass each. The type checker sits between parsing and code
generation because it needs the whole tree, and because the compiler *uses*
what it resolves — a `+` between two values it proved are numbers compiles to
a different instruction. Annotations are consumed, not erased.

The sixth stage only happens to code that runs enough to earn it. A function
whose arithmetic the checker already proved numeric is lowered to a typed IR
and compiled to machine code with no type tests and nothing to deoptimise to —
which is the one thing a JavaScript engine cannot do, because JavaScript
promises nothing about a value until it sees one.

## Where to look

| I want to… | Start at |
| --- | --- |
| add a syntax form | `src/parser_*.c`, then `src/compiler_*.c` |
| add an opcode | `include/cscript/opcode.h` — the X-macro generates the enum *and* the dispatch table, so they cannot drift |
| add a built-in | `src/native.c`, or the `native_*.c` for that type |
| understand a slowdown | `make profile`, which prints the executed-opcode and opcode-pair tables |
| check a behaviour against JavaScript | write it in `examples/`, then `make test-node` |
| add a test case | `tests/cases/NAME.cx`, with its `.expected` **generated by Node** |
| work on the JIT | `src/jit.c` for tiering, `src/ir.c` for the lowering, `src/jitcode.c` for the arm64 encoder; `make test-jit` for correctness and `make bench-jit` for what it is worth |

## The rules this codebase holds itself to

**Every claim about speed is measured.** The README records the changes that
returned nothing — computed goto, NaN-boxing on speed — beside the ones that
worked. A prediction is not a result.

**Node is the oracle.** Expected output for a test case is *generated by Node*,
not written by hand, so a disagreement is a bug here rather than a difference
of opinion. The exception is the file that exists to demonstrate deliberate
divergences, which the harness requires to differ.

**A gap says what it is.** Anything unimplemented produces an error naming the
feature, never a syntax error several tokens later.

**Every build configuration, run on every change.** `make test` under UBSan,
`test-gc` collecting on every allocation, `test-switch` on portable switch
dispatch, `test-tagged` on 16-byte tagged values, `test-ir` running the JIT's
lowering *instead of* the interpreter, `test-node` against Node itself, and
`test-jit` running every program twice in one binary — compiler off, compiler
on — and requiring the two to agree. Each has caught bugs the default build
hid. The last two are how the compiler is verified at all: a golden file pins
what a program prints and says nothing about whether the two paths agree.

**A null result is a result.** The optimisations that returned nothing are
written down beside the ones that worked, because the reasoning that produced
them was the same reasoning. The most expensive lesson so far was a benchmark
that agreed with Node, ran the right binary, and measured nothing at all: the
compiled code it was timing had never been entered.
